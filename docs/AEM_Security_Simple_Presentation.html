AEM 6.5 Lightweight Security Architecture

AEM 경량 보안 필터 (security-simple)
아키텍처 설계 및 핵심 기능 기술서

Referer · HTTP Method · Parameter 3대 핵심 보안 검증기를 기반으로
OSGi 동적 서블릿 바인딩, 기본 정책(Default Policy) 자동 상속, 단계별 디버그 및 차단 원인(BlockedByConfig) 상세 로깅을 제공하는 고성능 Sling 서블릿 보안 프레임워크

1. RefererPolicyValidator
• 기본 신뢰 도메인(abc.com) 및 서블릿별 allowedReferrers 검증
• 외부 악성 사이트 경유 CSRF 및 무단 API 호출 차단 (SEC-40303)
2. MethodPolicyValidator
• 허용된 HTTP Method 화이트리스트 O(1) Set 검증
• 비인가 메소드(DELETE, PUT 등) 호출 원천 차단 (SEC-40501)
3. ParamPolicyValidator
• 필수/미정의 파라미터 통제, 길이·정규식·DSL 검증
• Path Traversal · SQL/JCR2 Injection · XSS 방어 (SEC-40001~9)

1. 핵심 3대 검증기 중심 경량화

  2) MethodPolicyValidator (HTTP 메소드 통제)
  3) ParamPolicyValidator (파라미터 심층 검증)
• 불필요한 런타임 오버헤드(세션/레이트리밋/응답 래핑 등) 제거로 처리 속도 극대화
• 전 클래스/메소드 한글 Javadoc 주석 및 디버그 로깅 완비
2. 선언적 보안 설정 & 기본 정책 상속
• 중앙 집중형 기본 정책 (SecurityFilter.config)
  - 기본 Referer(abc.com), 기본 Method(GET, POST), 공통 파라미터(page, size, keyword 등) 일괄 정의
• 서블릿 컴포넌트 선언적 바인딩 (@Component)
  - 각 서블릿이 security.methods, security.params 등 필요한 항목만 선언하면 OSGi가 자동 등록
• 계층적 상속 (inheritFrom)
  - 서블릿에 미지정된 설정은 defaultPolicy에서 자동 상속
3. 고성능 매칭 & 정밀한 차단 원인 로깅
• O(1) 해시 캐시 및 사전 컴파일 정규식
  - ConcurrentHashMap 기반 경로/ResourceType O(1) 조회
  - 모든 정규식을 init() 시점에 1회 사전 컴파일
• 차단 시 즉각적인 원인 파악 로깅
  - BlockedByConfig: 차단을 유발한 설정 규칙과 입력값
  - AppliedServletPolicy: 서블릿의 현재 전체 보안설정 요약
• 서블릿 바인딩/언바인딩 시 디버그 로그 출력 차단

SecurityFilter.evaluatePoliciesAndFindActive() 핵심 흐름
ServletPolicyRule matchedPolicy = servletSecurityConfig.findMatchingPolicy(request);
if (matchedPolicy == null || !matchedPolicy.isEnabled()) return matchedPolicy;

for (PolicyValidator validator : validators) { // REFERER -> METHOD -> PARAM
    if (!validator.isEnabled(matchedPolicy, servletSecurityConfig)) continue;
    ValidationResult result = validator.validate(request, matchedPolicy, servletSecurityConfig);
    if (!result.isValid()) {
        String appliedPolicyInfo = formatAppliedPolicyForLog(matchedPolicy);
        String blockedConfigInfo = result.getBlockedConfig();
        handleSecurityViolation(request, response, matchedPolicy, validator.getName(),
            result.getStatusCode(), result.getSubCode(), result.getViolationDetail(),
            blockedConfigInfo, result.getResponseMessage());
        return REJECTED_POLICY;
    }
}

06. DYNAMIC BINDING & INHERITANCE
OSGi 동적 서블릿 바인딩 및 기본 정책 상속 메커니즘
07 / 15
OSGi @Reference 동적 바인딩 & 로그 노이즈 차단
• @Reference(service = Servlet.class, cardinality = MULTIPLE, policy = DYNAMIC)
• sling.filter.pattern과 일치하는 서블릿만 선별하여 dynamicPolicies에 자동 등록
• 바인딩/언바인딩 디버그 로그 출력 차단: 수많은 서블릿이 바인딩/언바인딩될 때 로그가 폭증하지 않도록 bindServlet, unbindServlet, registerDynamicPolicy 내부 로그 완전 제거
기본 정책 상속 및 병합 (ServletPolicyRule.inheritFrom)
• 서블릿에 명시하지 않은 설정은 SecurityFilter.config의 defaultPolicy에서 자동 상속
• AllowedReferrers: 기본 abc.com + 서블릿 고유 허용 도메인 합집합 병합
• Params: 기본 공통 파라미터(page, size, sort, order, lang, keyword) + 서블릿 파라미터 병합 (동일 키는 서블릿 규칙 우선)
기본 정책(Default Policy) + 개별 서블릿 프로퍼티 병합 예시
[1] Default Policy (SecurityFilter.config)
    methods=[GET, POST], defaultReferrer="abc.com", blockSqlInjection=true, blockXss=true, allowUndefinedParams=false,

[2] UserProfileServlet (@Component 프로퍼티)
    sling.servlet.paths="/aemapi/user/profile", security.methods="GET", security.allowedReferrers="partner.abc.com",
    security.params=["userId:required:alnum:4..20", "tab:optional:profile|settings|activity:15"]

[3] source=com.example.security.servlets.UserProfileServlet, target=/aemapi/user/profile, methods=[GET],

[Tier 1] 정적 설정 경로 O(1) 일치

[Tier 2] 동적 서블릿 경로 O(1) 일치
조회 맵: dynamicPolicies.get(uri)

[Tier 3] Sling ResourceType O(1) 일치
조회 맵: exactResourceTypePolicies.get(rt)
SlingHttpServletRequest의 resource.getResourceType()과 정확히 일치하는 정책을 O(1) 조회합니다.
[Tier 4] 정규식 · 하위경로 · 계층 매칭
조회 리스트: patternAndHierarchyPolicies
정규식 패턴 타겟(^/aemapi/v1/.*) 또는 resource.isResourceType() 상위 계층 일치를 검사합니다.
[Tier 5] 동적 서블릿 정규식/계층 매칭
조회 대상: dynamicPolicies.values()
동적으로 바인딩된 서블릿 중 정규식 패턴 또는 리소스 타입 상속 계층을 가진 정책을 매칭합니다.
[Tier 6] 기본 정책 폴백 (Fallback)
조회 대상: defaultPolicy (DEFAULT)
개별 정책이 없는 서블릿 요청에도 defaultPolicy를 자동 적용하여 보안 공백을 방지합니다.
08. VALIDATOR #1

09 / 15
RefererPolicyValidator 핵심 동작 및 매칭 규칙
• 검증 목적: 신뢰된 도메인(abc.com) 및 허용된 파트너 도메인 외의 외부 사이트에서 유입되는 CSRF 공격·무단 API 호출 차단
• 4가지 도메인/URL 매칭 방식 지원:
  1) 일반 도메인: abc.com 설정 시 abc.com 및 서브도메인(www.abc.com, m.abc.com) 자동 허용 (evilabc.com은 차단)
  2) 와일드카드 도메인: *.partner.co.kr
  3) 전체 URL 접두사: https://partner.com/app/
  4) 정규식 패턴: ^https://([a-z0-9-]+\.)?trusted\.org(/.*)?$
• 차단 응답: HTTP 403 Forbidden (SEC-40303)
RefererPolicyValidator 검증 및 BlockedByConfig 로깅
String referer = request.getHeader("Referer");
if (StringUtils.isBlank(referer)) {
    String blockedConfig = "defaultReferrer=" + defaultReferrer
        + ", allowedReferrers=" + policy.getAllowedReferrers()
        + ", requestReferer=MISSING";
    return ValidationResult.errorWithConfig(
        SecurityErrorCode.REFERER_INVALID, blockedConfig, ...);
}

// 1순위: defaultReferrer (예: "abc.com") 매칭 검사
if (isRefererAllowed(refererLower, refererHost, defaultReferrer)) {
    return ValidationResult.ok();
}
// 2순위: 서블릿별 allowedReferrers 목록 매칭 검사
for (String allowed : policy.getAllowedReferrers()) {
    if (isRefererAllowed(refererLower, refererHost, allowed)) {
        return ValidationResult.ok();
    }
}
09. VALIDATOR #2
MethodPolicyValidator — HTTP Method 화이트리스트 통제
10 / 15
MethodPolicyValidator 핵심 기능
• 화이트리스트 기반 HTTP 메소드 통제:
  - 허용 표준 메소드: GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS
• O(1) 대문자 해시셋(upperMethods) 매칭:
  - init() 시점에 대문자 불변 Set<String>으로 변환하여 매 요청 시 O(1) 조회
• 설정 우선순위:
  1) 다중 경로 서블릿의 경로별 설정 (/aemapi/order/cancel:POST)
  2) 서블릿 공통 설정 (security.methods=POST)
  3) 전역 기본 정책 폴백 (default.methods=["GET","POST"])
• 차단 응답: HTTP 405 Method Not Allowed (SEC-40501)
MethodPolicyValidator 구현 및 차단 로그 예시
@Override
public ValidationResult validate(HttpServletRequest request,
        ServletPolicyRule policy, ServletSecurityConfig rootConfig) {
    String method = request.getMethod();
    if (!policy.isMethodAllowed(method)) {
        String blockedConfig = "allowedMethods=" + policy.getMethods()
                + ", requestMethod=" + method;
        LOG.debug("[METHOD] 허용되지 않은 HTTP 메소드로 차단 - target=[{}], BlockedByConfig=[{}]",
                policy.getTarget(), blockedConfig);
        return ValidationResult.errorWithConfig(
                SecurityErrorCode.METHOD_NOT_ALLOWED,
                blockedConfig,
                "Method [" + method + "] not allowed",
                method);
    }
    return ValidationResult.ok();
}
10. VALIDATOR #3
ParamPolicyValidator — 6단계 심층 파라미터 보안 검증
11 / 15
Step 1. 필수 파라미터 검증 (SEC-40001)
required=true로 설정된 파라미터가 요청에 누락되었거나 공백 문자열인 경우 즉시 400 차단
BlockedByConfig: param=email, required=true, actualValue=MISSING
Step 2. 미정의 파라미터 차단 (SEC-40002)
allowUndefinedParams=false(기본값)일 때 정책에 명시되지 않은 파라미터 유입 시 즉시 차단 (Mass Assignment 방어)
Step 3. Path Traversal 차단 (SEC-40007)
../, ..\, %2e%2e%2f, 이중 인코딩(%252e), ..;/, Null 바이트(%00) 경로 조작 공격 차단
Step 4. SQL & JCR2/XPath 차단 (SEC-40008)
표준 SQLi(UNION SELECT, OR 1=1, SLEEP) 및 AEM JCR-SQL2(ISDESCENDANTNODE) · XPath(/jcr:root/) 차단
Step 5. XSS 공격 패턴 차단 (SEC-40009)
<script>, onerror=, javascript:, eval(), HTML 엔티티 인코딩(&lt;script&gt;) 우회 공격 차단
Step 6. 길이 & 정규식 검증 (SEC-40003~5)
minLength / maxLength 글자 수 검사 및 사전 컴파일된 정규식(compiledPattern) 포맷 일치 검증
